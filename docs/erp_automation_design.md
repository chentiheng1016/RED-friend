# 小紅 ERP 瀏覽器自動化 — 設計文件

- 狀態：草案 v1（2026-06-20）
- 範圍：客戶訂單**自動建立**（Phase 1）
- 作者：Claude（與大王討論中）

---

## 0. 摘要（先讀這段）

讓小紅透過瀏覽器（Edge/Chrome）操作公司 ERP，把客戶訂單自動填進「訂單建立」畫面。

**最高鐵則：小紅只負責「填到送出前」，最後那顆送出鍵一定要人工 `+確認` 才按。**
ERP 是公司帳本，填錯一筆 = 錯訂單 = 錯生產採購，絕不盲目自動下單。

- 技術：小紅讀單＋對應欄位（LLM）＋ Playwright 確定性填表（穩、可稽核）＋ 人工確認閘門。
- 知識來源：剛建好的 `operation_sops`（影片 SOP）＝「填哪個畫面、哪個欄位、預設值、易錯點」的操作手冊。
- 最難：客戶 PO 識別碼 ↔ ERP 識別碼的對照表（物號/型體/PO#/客戶碼）。
- 落地：5 個階段，每階段在**測試 ERP**驗證、只前進一步；先只做「業務訂單建立」一個操作。
- ⚠️ 若 ERP 廠商（VNR.IT）有 **API**，優先走 API——比瀏覽器自動化穩太多。瀏覽器自動化是「沒 API 時的辦法」。

---

## 1. 目標與非目標

**目標（Phase 1）**
- 輸入：一張客戶訂單（信件／PDF／Drive `4-客戶-訂單` 夾）。
- 小紅自動：登入 ERP → 進訂單建立畫面 → 填好表頭＋明細 → 產出「草稿截圖＋填入摘要」→ 推給大王 → `+確認` 後才送出 → 回讀訂單號。
- 範圍只有「業務訂單建立」這一個操作。

**非目標（這版不做）**
- 全自動、無人確認的下單。
- 一次做所有操作（採購／領料／入庫…）。
- 修改既有單據、刪除、財務過帳、審核流程。
- 在沒有測試環境的情況下直接上正式機。

| 資產 | 用途 |
|---|---|
| `operation_sops` + `search_operation_sops` | 操作手冊：哪個畫面、哪些必填欄位、預設值、易錯點 |

| keyring secrets 慣例 | 存 ERP 專屬帳號憑證 |

## 3. 威脅模型與安全原則（最重要，務必先讀）

ERP 是**系統 of record（公司帳本）**，自動寫入風險遠高於讀取。鐵則：

1. **草稿—確認—送出**：小紅只能把表單「填到送出前」。`送出/存檔/確認` 那顆按鈕**一定**經大王 `+確認` 才按。policy_engine 把此操作定為 **LOCKED / DANGEROUS tier**。
2. **冪等與去重**：同一張客戶訂單不可重複建單。建單前先查 ERP 是否已有同 PO# 的單；建完記錄「PO# → ERP 訂單號」，再跑一次直接跳過。
3. **全程稽核**：每一步（登入、進畫面、每欄填什麼值、送出與否）寫 `var/runs/erp_automation/`，附送出前後截圖。出事可回溯小紅填了什麼。
4. **最小權限**：小紅用**專屬 ERP 帳號**（非大王本人），權限只開到「建訂單」。
5. **先測試環境**：開發、調 selector、跑流程，全在**測試/沙箱 ERP**。正式機只在流程穩定後、單筆、人盯著上。
6. **Kill switch**：一個旗標能立刻停掉所有 ERP 自動化（沿用 `RED_BLOCK_TOOL` 那層）。
7. **不可逆動作絕不自動**：刪除、覆蓋既有單、財務過帳，永遠人工。
8. **填入即驗證**：填完每格回讀畫面確認（填 `10001` 要讀回 `10001｜NEW WAVE`），不一致就停、報告，不硬送。

## 4. 整體架構

```
 客戶訂單(信/PDF/Drive夾)
        │  ① 擷取
        ▼
 [訂單解析器] ── 結構化訂單(客戶,款號,數量,交期,PO#…)
        │  ② 對應(查 operation_sops + 識別碼對照表)
        ▼
 [欄位對應器] ── ERP 填表計畫(每個 ERP 欄位 = 什麼值)
        │  ③ 驅動
        ▼
 [ERP 瀏覽器驅動(Playwright)] ── 登入→進畫面→填欄位→**停在送出前**
        │  ④ 草稿
        ▼
 [確認閘門] ── 截圖+填入摘要 → Telegram 推給大王 → +確認 ?
        │                                    │ 否 → 放棄/記錄
        ▼ 是
 [送出] → 回讀 ERP 訂單號 → 記錄 PO#→訂單號 + 稽核
```

**元件落點（建議新套件 `agent_core/erp_automation/`）**
- `order_parser.py`：訂單 → 結構化（複用現有郵件/PDF 抽取）。
- `field_mapper.py`：結構化訂單 + 對照表 → ERP 填表計畫。
- `erp_driver.py`：Playwright 封裝（登入、導航、填、回讀、截圖）。
- `screen_map/`：每個 ERP 畫面的欄位 selector 對照（recon 建出）。
- `confirm_gate.py`：草稿摘要 + 截圖 + `+確認` 整合。
- `run_record.py`：稽核記錄。
- 工具層：`erp_create_order_draft(order_ref)`（小紅可呼叫，tier=DANGEROUS/LOCKED）。

## 5. 識別碼對照（最難的一塊，單獨拉出來）

之前對帳就卡在這（見 LURCHI 案）：
- 客戶 PO 上：物號 `63L`／客戶 PO# `2026260…`。
- ERP 裡：型體 `EJ/EG/EH`／指令 `JFCnn`／客戶碼 `10001`。

自動填表的前提是這兩套對得上。方案：
1. **建一張對照表**（先 CSV，後 DuckDB/SQLite）：`客戶物號 ↔ ERP 型體 ↔ 客戶碼 ↔ 品名`。
   資料來源：Drive 訂單夾 BOM/分析表、**ERP 料號/客戶主檔匯出**、歷史已建單回填。
2. **對得到才自動、對不到就停**：mapper 查不到就把該行標「需人工」，**不亂猜**（寧可漏不可錯）。
3. 與 `docs/factory_warehouse_design.md` 的 identifier crosswalk 是同一份資產，共用。

> 這塊建議當**獨立前置工程**先做——沒有它，自動填表填不準。

## 6. 瀏覽器自動化層

**選型**
| 路線 | 優 | 劣 | 用在 |
|---|---|---|---|
| **Playwright 確定性 selector** | 快、可靠、可稽核、可重播 | selector 會因 ERP 改版斷、要 recon | **主力**（填表執行） |
| LLM 看畫面點（Gemini/Claude computer-use、Chrome MCP） | 適應畫面變化、免維護 selector | 慢、會點錯、token 貴 | recon、fallback、selector 斷時救援 |
| 純錄製重播 | 簡單 | 最脆 | 不建議 |

**建議**：主力 **Playwright**（穩、可稽核），LLM-vision 當 recon 工具（第一次摸畫面、建 selector map）＋ fallback。

**技術地雷（Phase 0 勘查就是要看這些）**
- **iframe**：老 ERP 常把內容包在 frame，要先切 frame 才定位得到。
- **動態 element id**：別綁 id，用穩定屬性／label 文字／相對定位。
- **session timeout**：要偵測被踢回登入頁→自動重登一次→失敗就停。
- **表格列動態載入**：填明細前要等資料載完。
- 登入憑證走 keyring（不寫死）；Edge/Chrome 皆可（Playwright 支援 chromium / msedge channel）。

## 7. 草稿—確認—送出流程（核心安全流程）

1. driver 登入 → 進訂單建立畫面。
2. mapper 算出填表計畫；driver 逐欄填、**每填一格回讀驗證**。
3. 填完（含明細各行），**停在送出按鈕前**，不按。
4. 截圖整個畫面 + 產出「我填了什麼」結構化摘要（欄位=值清單）。
5. 推 Telegram 給大王：截圖 + 摘要 + 「要送出嗎？回 +確認」。
6. 大王 `+確認` → driver 按送出 → 等 ERP 回應 → 回讀訂單號 → 記錄 + 回報成功。
7. 不確認/逾時 → driver 放棄（關畫面不存）→ 記錄「草稿已棄」。
8. 任一步 ERP 跳錯（必填漏／驗證失敗／對照不到）→ 停、截圖、原文回報，**不硬送**。

## 8. 分階段落地（每階段都在測試 ERP 驗證、過了才下一階；一階段一個 PR）

- **Phase 0 — 可行性勘查**（無寫入）：瀏覽器打開訂單畫面，勘查 DOM（iframe？動態 id？）、能否穩定定位欄位、能否程式登入。產出：可行性報告 + 風險清單。**這是現在就能先做的。**
- **Phase 1 — 唯讀導航**：Playwright 登入＋導到訂單畫面＋讀出畫面欄位（證明驅動得動、讀得到），完全不填。
- **Phase 2 — 填到草稿**（測試 ERP）：填表頭＋明細、回讀驗證、**停在送出前**、截圖、**不送**。先用人工準備的一張測試單、欄位值寫死。
- **Phase 3 — 確認＋送出**（測試 ERP）：加 Telegram 草稿摘要 + `+確認` 閘門 + 送出 + 回讀訂單號。跑通一張測試單完整迴圈。
- **Phase 4 — 訂單擷取＋對應**：接上「從真實客戶訂單自動擷取＋查對照表算填表計畫」（前面是寫死值，這階段才自動算）。需識別碼對照表（§5）就緒。
- **Phase 5 — 正式機試營運**：挑**一個客戶**、單筆、人盯著，正式機跑。穩了再放寬。

## 9. 資料模型（草案）

結構化訂單：
```json
{
  "source": {"type": "email|drive_pdf", "ref": "<id>"},
  "customer": {"name": "NEW WAVE", "erp_code": "10001"},
  "po_number": "2026260...",
  "season": "AW26",
  "lines": [
    {"customer_item": "63L", "erp_model": "EJ...", "qty": 8058,
     "delivery": "2026-09-15", "_mapped": true}
  ],
  "unmapped_lines": []
}
```
填表計畫：`[{screen:"FTE_570", field:"訂單類別", value:"01", verify:true}, …]`
對照表：`crosswalk(customer_item, erp_model, erp_customer_code, name, source, confidence)`

## 10. 錯誤處理與復原
- selector 斷 → 停、截圖、報「畫面變了，需重建 screen_map」，不亂點。
- session 逾時 → 偵測登入頁 → 重登一次 → 失敗就停。
- ERP 驗證錯（必填漏／格式錯／重複單）→ 把 ERP 錯誤訊息原文回報，不硬送。
- 草稿填一半失敗 → 不存（關畫面），不留半張髒單。
- 可重播：記錄填表計畫，人可照著手動重做。

---

## 11. 可觀測性與稽核
- 每次跑寫 `var/runs/erp_automation/<ts>.json`：輸入訂單 ref、填表計畫、每欄回讀結果、是否送出、ERP 訂單號、截圖路徑。
- 送出前後各一張截圖。
- LLM 解析＋對應的 token 成本進 cost dashboard。
- 月報：自動建幾單／幾單需人工／錯在哪。

## 12. 開放問題與前置條件（需要大王／IT 提供）
1. **有沒有測試/沙箱 ERP？**（最關鍵；沒有的話 Phase 0–4 怎麼安全做要另想）
2. ERP 網址、登入方式（帳密／SSO／要不要 VPN），能否開一個**專屬自動化帳號**。
3. ERP 能否匯出**料號／客戶主檔**（建識別碼對照表用）。
4. 小紅那台機器到 ERP 的網路可達性（內網／VPN）。
5. 試營運先挑哪個客戶（建議單純、量穩的那個）。
6. **ERP 廠商（VNR.IT）能否給 API？** 有的話很多操作可繞過瀏覽器、更穩，值得先問。

---

## 13. 風險與明確不做
- ERP 改版 → selector 全斷：靠 `screen_map` 集中管理 + LLM fallback，但仍是長期維護成本。
- 對照表不全 → 填錯料號：用「對不到就停」防。
- 正式機誤送：用 `+確認` 閘門 + 專屬低權帳號 + kill switch 三層防。
- **明確不做**：自動審核、自動過帳、自動刪改既有單、無確認的批量下單。

---

> 結論：方向可行，`operation_sops` 已是現成操作手冊。但這是「寫公司帳本」的工程，價值高、風險也高，必須**草稿+人工確認、先測試環境、先一個操作、分階段**。先做 Phase 0 可行性勘查（無寫入、低風險、高資訊），再決定值不值得投入。**先確認有沒有 API 與測試環境**是兩個最關鍵的前置。
